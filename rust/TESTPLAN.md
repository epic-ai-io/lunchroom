# Lunchroom test plan

This file maps each of the 182 requirements of `docs/spec/lunchroom-spec.md` (words per `docs/spec/standard-vocabulary.md`) to the test that proves it. Every requirement has a test name: a Rust test function in the Rust workspace (`rust/crates/`), or a plugin's own test under `rust/plugins/`. A test may serve more than one requirement only where it checks each requirement's acceptance criterion, and a requirement whose criterion needs two tests lists both. A few requirements are checks by reading the product or its documentation (method `Inspection`); those are marked as such.

Requirement ids: each row is one requirement, written `clause/number`. The clause is the spec clause (`R1` is spec §2, `A1` is §7, and so on: V1, R1, R2, R3, T1, P1, A1, A2, I1, D1, L1, F1, H1, C1, K1 in spec order, and `Cards` for §16), and the number is the requirement's place among those the clause states. One numbered item of a clause can hold several requirements, so the numbers do not always equal the item numbers in the spec (requirement `R1/5`, for example, is the halt at the eighth identical message, which spec item R1.3 states).

Scope: the core library (vocabulary, permission slip, PROTECTED, YOLO decisions, loop halt, secret checks, identity, delivery store, exact-call approvals, card lines), the hook adapters for Claude Code and Codex, and the plugin adapters for OpenClaw and Hermes. The OpenClaw and Hermes plugins are tested against stand-ins of those harnesses; live runs of both are described in `docs/host-facts/openclaw-and-hermes.md`. Claude Code's own permission prompt is the approval channel for Claude Code, and `lunchroom approve` from a terminal is the channel for any harness. Rows marked `later` in the area column are release-time inspections of the documentation or the finished release, or the cockpit beyond the user's terminal; they have no test yet. Where a row names the harnesses or parts of a requirement it covers, the row's text says what it covers and what it leaves out.

Status, in plain words:

- `written`: a test checks the requirement's whole acceptance criterion.
- `decision`: the rule is tested as a decision on an already-classified call (`policy::decide`); it is not yet tested with a real call end to end. The row says so.
- `partial`: a test checks part of the acceptance criterion, and the row says what is not covered (for example, a stand-in in place of a running harness, or a run at a person's real terminal).
- `inspect-ready`: an inspection whose code is in place, ready for a person to read.
- `todo`: nothing is written yet; the row says what is needed.

Requirements are ordered by clause number, then by number within the clause.
